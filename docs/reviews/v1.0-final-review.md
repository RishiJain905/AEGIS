## AEGIS-BUG-001 — Non-atomic event sequence assignment (read-max-plus-one under no lock)

- **Severity:** Critical
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Inferred (code-path proven; concurrency window not driven live)
- **Affected component:** persistence / event streaming; every command handler that appends events
- **Affected files:**
  - `packages/persistence/src/aegis_persistence/repositories/postgres.py:270-278` (`next_sequence`)
  - `packages/persistence/src/aegis_persistence/unit_of_work.py:255-256`
  - `packages/persistence/src/aegis_persistence/orm/tables.py:123` (`uq_domain_events_run_sequence`)
  - Call sites: `apps/api/src/aegis_api/approvals/service.py:222,330,470,484,596,676,801`; `services/agents/src/aegis_agents/runtime/executor.py:205,456,513,561`; simulation command paths.

**Reproduction steps**
1. Pick a run with existing events.
2. Concurrently issue two operations for the same `run_id` that each append an event in separate `PostgresUnitOfWork` transactions (e.g. an approval `POST /approvals/.../approve` and an agent task execute, or two agent task executes).
3. Both transactions call `next_sequence(run_id)` before either commits.

**Expected:** sequence numbers are assigned atomically and monotonically per `(run_id, sequence)`, as required by `docs/architecture.md` ("unique monotonic `(run_id, sequence)`", "append-only").

**Actual:** `next_sequence` runs `SELECT sequence ... WHERE run_id=? ORDER BY sequence DESC LIMIT 1` and returns `current+1` with **no row lock, no advisory lock, and no DB sequence**. Two concurrent transactions read the same max and compute the same next value. Because `uq_domain_events_run_sequence` exists, the second `COMMIT` fails with an `IntegrityError`, rolling back an otherwise-valid command (approval execution, agent step, lifecycle command). Without the constraint it would silently duplicate a sequence.

**Technical cause:** sequence generation is a non-atomic read-compute-write straddling the transaction boundary; correctness depends on there never being two concurrent writers for one run, which is not enforced anywhere.

**Impact:** Under any concurrent same-run write (approval + agent, two agents, backfill + lifecycle), one operation fails with a 500/rollback. This is a direct violation of a named non-negotiable invariant and undermines the "PostgreSQL is the sole source of truth, events are atomic and monotonic" guarantee.

**Recommended fix:** Assign sequence inside the same transaction atomically — either a Postgres sequence/`GENERATED` column scoped per run, or `INSERT ... SELECT COALESCE(MAX(sequence)+1, 0)` guarded by a per-run advisory lock (`pg_advisory_xact_lock(hashtext(run_id))`) taken at the start of every appending command, or `SELECT ... FOR UPDATE` on a per-run counter row. Retry-on-unique as a fallback is not sufficient alone.

**Suggested regression test:** Integration test that fires two concurrent `append_event` transactions for the same run via `asyncio.gather` and asserts both commit with distinct consecutive sequences (no `IntegrityError`).

## AEGIS-BUG-002 — Agent task-claim race: a QUEUED task can be executed twice

- **Severity:** High
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Inferred (code-path proven)
- **Affected component:** agent runtime worker + API inline execution
- **Affected files:**
  - `services/workers/src/aegis_workers/agent_runtime_runner.py:19-33` (`_poll_once` lists QUEUED then executes in a separate UoW)
  - `services/agents/src/aegis_agents/runtime/executor.py:120-128` (status read), `:188-196` (unconditional flip to RUNNING via plain `update`)
  - `apps/api/src/aegis_api/agents/router.py:60-80, 90-112, 123-133` (API creates a task, then executes it inline in a *separate* UoW)

**Reproduction steps**
1. Run the agent runtime worker (`uv run aegis-worker --mode ...`) and the API concurrently.
2. `POST /api/v1/agent-sessions/{id}/tasks`. The API commits the QUEUED task in one UoW, then opens a second UoW to execute it.
3. In the window between those two UoWs, the worker's `_poll_once` lists the same QUEUED task and executes it. Both readers see `status == QUEUED`.

**Expected:** exactly one executor claims and runs a QUEUED task.

**Actual:** `TaskExecutor.execute` reads the task and returns early only if `status != QUEUED` (`executor.py:127`), then `_execute_body` flips to RUNNING with an unconditional `uow.agent_tasks.update(running)` (`:196`) — no `WHERE status=QUEUED` claim, no row lock, no optimistic revision (contrast `incidents.update_with_revision`). Two readers both pass the QUEUED check and both run the task: duplicate `task.started/tool.invoked/task.completed` events, duplicate tool invocations, duplicated provider cost, and (for BASTION/WARDEN) potentially duplicated proposals.

**Technical cause:** claim is a check-then-act across transactions with no atomic status transition.

**Impact:** Duplicate agent execution and duplicated authoritative events; also amplifies AEGIS-BUG-001 (two writers on one run).

**Recommended fix:** Atomic claim: `UPDATE agent_tasks SET status='running', started_at=now() WHERE id=? AND status='queued' RETURNING ...`; treat zero rows updated as "already claimed" and return. Apply the same pattern to `retry`.

**Suggested regression test:** Integration test that enqueues one task and invokes two `executor.execute` calls concurrently; assert exactly one produces a `task.started` event and the other no-ops.

## AEGIS-BUG-003 — Approval double-execution race (idempotency keyed to caller key, not proposal identity)

- **Severity:** High
- **Confidence:** Medium-High
- **Directly-Reproduced-or-Inferred:** Inferred (code-path proven)
- **Affected component:** approvals workflow
- **Affected files:**
  - `apps/api/src/aegis_api/approvals/service.py:148-171` (idempotency check on `request.idempotency_key`; unconditional `_require_proposal`/`_assert_pending`)
  - `:217-220, 261-267` (proposal status flips via plain `update_proposal`, no optimistic guard)
  - `:709-748` (`_execute_authorized` dedups on caller `idempotency_key`, and `command_id = idempotency_key`)

**Reproduction steps**
1. Create a PENDING proposal.
2. Two approvers (both holding `approvals:decide`) `POST .../approve` concurrently, each with a **different** `Idempotency-Key` but the same `expected_revision` / `expected_revision_id`.
3. Both pass the idempotency lookup (different keys → both miss), both read the proposal as PENDING (before either commits), both pass `_assert_pending` and `_assert_revision_match`, both pass final WARDEN revalidation, both execute.

**Expected:** a proposal executes at most once; the second concurrent approve is rejected (409 already-decided) or replayed.

**Actual:** `update_proposal` (`:220`, `:267`) has no `expected_revision` guard (unlike `incidents.update_with_revision` at `:847`). `_execute_authorized` dedups only on `run_id + idempotency_key`; with different keys the executed-action guard misses and `command_id` differs, so the simulation `DUPLICATE_COMMAND` guard also misses. Both approvals execute the same containment action.

**Technical cause:** the approval transaction is not serialized on proposal identity; uniqueness is anchored to a caller-supplied idempotency key rather than to `(proposal_id, revision)`.

**Impact:** Double execution of an approved Class 2/3 containment (e.g. isolate/revoke) — a trust-boundary and authoritative-state violation for the human-approval gate.

**Recommended fix:** Anchor idempotency/uniqueness to proposal identity: take a per-proposal advisory lock or `SELECT ... FOR UPDATE` on the proposal at the top of `approve`, and/or make `update_proposal` optimistic (`WHERE revision = expected`). A unique executed-action key of `(proposal_id, approval decision)` rather than free-form idempotency key closes the execution side.

**Suggested regression test:** Concurrent double-approve of one proposal with two distinct idempotency keys; assert exactly one `ExecutedActionV1` row and one `action.executed` event.

## AEGIS-BUG-004 — Scoring fingerprint collision: stale score returned (lossy input checksum)

- **Severity:** High
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Directly reproduced by the prior reviewer (two fact sets → 94.3 vs 84.3, identical fingerprint); confirmed here by code analysis of the exact omitted fields.
- **Affected component:** scoring
- **Affected files:**
  - `services/scoring/src/aegis_scoring/engine.py:35-80` (`_input_checksum`), `:162-172` (fingerprint)
  - `services/scoring/src/aegis_scoring/service.py:87-97` (returns `existing`/`latest` by fingerprint)
  - Score-affecting fields absent from the checksum: `services/scoring/src/aegis_scoring/criteria.py:107-110` (`evidence.summary` drives coverage matching) and `:378-386` (`executed_actions.target_asset_ids` drives false-positive-cost)

**Reproduction steps**
1. Score a completed run → `RunScoreV1` persisted with fingerprint F, overall S1.
2. Change only a field the score depends on but the checksum ignores — e.g. `executed_actions[].target_asset_ids` (moves a containment onto/off the true-cause asset chain) or an `evidence[].summary`.
3. Re-score. `_input_checksum` is unchanged (it only serializes event `{eventId,sequence,eventType,assetId}`, evidence `{evidenceId,sourceEventId,assetId}`, action `{actionId,proposalId,outcome,impactScore}`), so fingerprint F is unchanged, but the computed overall is S2 ≠ S1.
4. `score_run` finds the stored score by fingerprint and returns the stale S1 (`service.py:87-89`, `:92-94`).

**Expected:** the fingerprint is a total function of every input that can change the score; different scores never share a fingerprint.

**Actual:** `_input_checksum` is lossy. It omits `executed_actions.target_asset_ids`, `evidence.summary`, `facts.proposals`, `facts.objectives`, `facts.expected_evidence`, and `facts.response_branches` — all of which feed criterion handlers (`criteria.py`). Two genuinely different scorings collide on one fingerprint, and the stale prior score is returned.

**Technical cause:** the checksum captures a hand-picked subset of identity fields, not the full scoring input surface.

**Impact:** Authoritative after-action scores can be silently stale/incorrect — a correctness defect in the platform's evaluation output.

**Recommended fix:** Compute the checksum over the fully-serialized `ScoringFacts` (canonical JSON of the whole dataclass), or explicitly include every field consumed by any criterion handler; add a test that asserts every `ScoringFacts` field is covered.

**Suggested regression test:** Property/unit test: mutate each score-affecting `ScoringFacts` field in turn and assert the fingerprint changes whenever the overall score changes.

## AEGIS-BUG-005 — Restart recovery re-derives runtime by sim-event count, losing lifecycle + executed-action state

- **Severity:** High
- **Confidence:** Medium-High
- **Directly-Reproduced-or-Inferred:** Inferred (code-path proven; determinism reproduction not executed here)
- **Affected component:** simulation restart/recovery vs replay contract
- **Affected files:** `services/simulation/src/aegis_simulation/run_command_service.py:238-286` (`_get_or_restore_runtime`)

**Reproduction steps**
1. Start a run, advance it, then pause/stop it or approve a Class 2/3 containment that mutates world state (e.g. isolate an asset).
2. Evict the in-memory runtime cache (process restart) so `_get_or_restore_runtime` runs.
3. Issue any command that restores the runtime.

**Expected:** per `docs/architecture.md`, historical/authoritative state is reconstructed from snapshots + the persisted event stream, preserving lifecycle status and executed-action effects.

**Actual:** recovery creates a **fresh seeded runtime**, `runtime.start()`, counts `db_events` whose type starts with `sim.` (`:266`), then blindly `runtime.step()`s until `len(runtime.events) >= sim_event_count` (`:268`). It never inspects `run.status` (paused/stopped) and never replays approval/agent/execute commands. Executed-containment effects (applied via `execute_command`, not by stepping) are not re-applied; if their events are counted as `sim.*` the step target is inflated and the runtime advances **past** its true position, diverging state.

**Technical cause:** recovery reconstructs by event *count* rather than by replaying the stored command/event history; it conflates "same number of sim events" with "same authoritative state."

**Impact:** A paused/stopped/contained run can restore as an unrelated running state — an authoritative-state and determinism violation that also feeds incorrect state into any subsequent command executed against the restored runtime.

**Recommended fix:** Restore from the latest snapshot + deterministic replay of the persisted event stream (the replay engine already reconstructs state), and explicitly restore `run.status` and executed-action world effects; never advance a fresh runtime by count.

**Suggested regression test:** Persist a run paused at sequence N with an executed containment; restore; assert restored status == paused and the contained asset's state matches, not merely event count.

## AEGIS-BUG-006 — Agent runtime worker has no graceful shutdown drain

- **Severity:** Medium
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Inferred (code-path proven)
- **Affected component:** workers
- **Affected files:** `services/workers/src/aegis_workers/agent_runtime_runner.py:52-58` (`main`), `:36-49` (`_run_loop`)

**Reproduction steps:** Send SIGTERM/SIGINT to the agent runtime worker while a task is mid-execution.

**Expected:** in-flight `executor.execute()` drains (like the outbox relay's `stop_event` graceful stop).

**Actual:** the signal handler calls `sys.exit(0)` immediately, aborting the running task mid-transaction. The task is left RUNNING and relies on `recover_running_tasks` at next startup (`:41-42`).

**Technical cause:** no cooperative stop event; hard exit in the signal handler.

**Impact:** Orphaned RUNNING tasks on every restart/redeploy; partial event streams until recovery. Lower severity because a recovery path exists.

**Recommended fix:** Use an `asyncio.Event` stop signal (mirroring the outbox relay), finish the current task, then exit.

**Suggested regression test:** Unit test asserting the loop exits only after the in-flight `execute` future resolves when the stop event is set.

## AEGIS-BUG-007 — Live-view state divergence between reducer revision counter and graph store

- **Severity:** Low
- **Confidence:** Low
- **Directly-Reproduced-or-Inferred:** Inferred (derived from the prior reviewer's "two live-view divergence paths" narrative; not independently reproduced)
- **Affected component:** web realtime live view
- **Affected files:** `apps/web/lib/realtime/run-reducer.ts:91-102` (`apply_graph_delta` bumps only `graphRevision`), `:117-128` (`advance_sequence` dedups on `eventId`), `:67-90` (timeline dedups on `sequence`)

**Observations (what "two divergence paths" most plausibly refers to):**
1. The reducer stores the graph as a numeric `graphRevision` + `lastAppliedSequence` only; the actual node/edge geometry lives in a separate Sigma/Graphology store fed by deltas on a different path. During a `GAP`, the reducer freezes (returns state) but the two representations can drift if the graph store does not freeze identically, so `graphRevision` and the rendered graph can disagree until a snapshot resync.
2. Two different dedup keys coexist for one stream — timeline/graph deltas dedup on `sequence` (`:68,79,92`) while `advance_sequence` dedups on `eventId` (`:127`), and `seenEventIds` grows unbounded. Interleaved application can advance `lastAppliedSequence` on one path and cause the other to treat a not-yet-applied item as already applied.

**Expected:** one authoritative live-state projection; 2D and 3D derive from it identically.

**Recommended fix:** Trace the live graph store vs reducer for gap/resync parity; unify the dedup key and bound `seenEventIds`. This finding needs a dedicated frontend trace before a fix is scoped.

**Suggested regression test:** Reducer test injecting out-of-order + duplicate deltas across a GAP→resync cycle asserting graph revision and applied-sequence stay consistent.

## AEGIS-OITB-001 — Systemic authorization gap: mutating endpoints reachable with read-only permission

- **Severity:** Blocker
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Inferred (permission-to-route mapping proven precisely from code; live 200-vs-403 not driven)
- **Affected component:** API router mounting / authorization placement
- **Affected files:**
  - `apps/api/src/aegis_api/main.py:171-222` (router mounts; `write_runs` constructed at `:172` but never attached, only lint-referenced at `:214`)
  - `packages/policy/src/aegis_policy/authz/matrix.py:22-31` (VIEWER holds `runs:read` + `investigation:read`, nothing else mutating)
  - Vulnerable routes below.

**Permission model (verified):** `VIEWER` = `{runs:read, investigation:read, replay:read, reports:read, scoring:read, ws:subscribe}` (matrix.py:22-31). Any authenticated VIEWER reaches every route mounted under `read_investigation`/`read_runs` unless the route adds its own stricter dependency.

**Mutating routes reachable by a VIEWER (no route-level write permission):**

Mounted under `investigation:read` (`main.py:192-202`):
| Method + path | File:line | Effect |
|---|---|---|
| `POST /api/v1/detection/evaluate` | `detection/router.py:36-62` | Persists alerts/incidents (`dry_run` defaults **False**, `contracts detection.py:323`) |
| `POST /api/v1/models/score` | `models/router.py:34-56` | Persists model detections (`dry_run` default False, `models.py:206`) |
| `POST /api/v1/models/verify-artifact` | `models/router.py:59-69` | Reads arbitrary filesystem paths from request body (`manifest_path`, `artifact_path`) |
| `POST /api/v1/risk/compute` | `risk/router.py:30-56` | Persists risk scores (`dry_run` default False, `risk.py:293`) |
| `POST /api/v1/features/compute` | `features/router.py:42-57` | Compute (read-only) — lower impact |
| `POST /api/v1/features/parity-check` | `features/router.py:60-72` | Compute (read-only) — lower impact |
| `POST /api/v1/agents/harness/seed` | `agents/router.py:41-45` | Seeds a harness incident (writes) |
| `POST /api/v1/incidents/{id}/agent-sessions` | `agents/router.py:48-80` | Creates a session and **executes an agent** |
| `POST /api/v1/agent-sessions/{id}/tasks` | `agents/router.py:90-112` | Creates and **executes an agent task** |
| `POST /api/v1/agent-sessions/{id}/cancel` | `agents/router.py:115-120` | Cancels a session (writes) |
| `POST /api/v1/agent-tasks/{id}/retry` | `agents/router.py:123-133` | Retries and **executes an agent** |

Mounted under `runs:read` (`main.py:187`):
| Method + path | File:line | Effect |
|---|---|---|
| `POST /api/v1/realtime/backfill` | `realtime/backfill.py:16-29` | Republishes persisted events to Redis (mass re-delivery to all WS subscribers) |

**Correctly protected siblings (proves the pattern was known and simply not applied uniformly):**
- Run mutations `POST /runs`, `/runs/{id}/{pause,resume,stop,step}` carry route-level `runs:write` (`runs/router.py:149,243,255,267,279`). **The prior narrative's claim that the run router is unprotected is REFUTED.**
- Investigation triggers require `investigation:trigger` (`investigation/router.py:44,66,85,105`).
- Report trigger/export require `reports:trigger`/`reports:export` (`reports/router.py:47,74`); approvals mount requires `approvals:decide` (`main.py:204`).

**Reproduction steps**
1. `POST /api/v1/auth/dev/login` as a VIEWER identity; keep the session cookie + CSRF token.
2. `POST /api/v1/agents/harness/seed` (or `/api/v1/detection/evaluate`, `/api/v1/risk/compute`, `/api/v1/realtime/backfill`) with the CSRF header.
3. Observe a 2xx and persisted DB writes / agent execution / Redis republish — despite the actor holding only read permissions.

**Expected:** state-mutating endpoints require a write/trigger permission (`investigation:trigger`, a new `detection:*`/`models:*`/`risk:*` write, or `admin:manage`). Per the architecture, state-changing agent actions are gated (proposals + human approval); a VIEWER must never enqueue/execute agents or persist detection/risk/model results.

**Actual:** these routers are mounted only under a read permission and their mutating routes add no stricter dependency, so `investigation:read`/`runs:read` is sufficient to mutate authoritative state.

**Technical cause:** write authorization was applied per-route in `runs`/`investigation`/`reports` but omitted in `detection`/`models`/`risk`/`features`/`agents`/`backfill`, which rely solely on the read-level router mount.

**Impact:** Privilege escalation for the lowest authenticated role: direct authoritative DB writes, agent execution (bypassing the proposal/approval trust model), harness data injection, arbitrary-path artifact reads, and mass Redis re-delivery. Release-blocking.

**Recommended fix:** Add route-level `require_permission(...)` write dependencies to every mutating route (or split each router into read vs write sub-routers mounted under the correct permission). Introduce dedicated write permissions for detection/models/risk if `investigation:trigger`/`admin:manage` is too coarse. Gate `verify-artifact` path inputs and `backfill` behind `admin:manage`. Add a contract test enumerating every POST/PUT/PATCH/DELETE route and asserting it requires a non-read permission.

**Suggested regression test:** Parametrized API test that, as a VIEWER, calls every mutating route and asserts 403; as the appropriate write role asserts 2xx.

## AEGIS-OITB-002 — Production OIDC authorization-code flow is a non-functional stub

- **Severity:** High
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Directly confirmed from code (unconditional raise)
- **Affected component:** auth (production login)
- **Affected files:**
  - `apps/api/src/aegis_api/auth/oidc.py:59-72` (`ConfiguredOidcProvider.exchange_code` always raises), `:126-129` (`create_oidc_provider` returns `ConfiguredOidcProvider` in **both** branches — the `if` is dead)
  - `apps/api/src/aegis_api/auth/startup.py:26-27` (production startup **requires** `AEGIS_OIDC_ENABLED=true`)
  - `apps/api/src/aegis_api/auth/router.py:223-284` (`/callback`)

**Reproduction steps**
1. Configure a production-like env (`AEGIS_ENV=production`, `AEGIS_OIDC_ENABLED=true`, issuer/client set).
2. `GET /api/v1/auth/login` → redirects to the IdP (works).
3. Complete IdP login → `GET /api/v1/auth/callback?code=...&state=...`.

**Expected:** the code is exchanged for tokens/claims and a session is created.

**Actual:** `exchange_code` unconditionally raises `AuthOidcError("OIDC token exchange requires a configured identity provider adapter")` — there is no real JWKS/token exchange. `create_oidc_provider` never returns anything else. Every production callback fails; combined with the startup guard forcing OIDC on in production (and dev auth off), **no user can authenticate in production.**

**Technical cause:** the OIDC adapter is a fail-closed placeholder; the production token-exchange integration was never implemented, and the provider factory has a dead branch.

**Impact:** Production is unusable for real login (fail-closed, so not a vulnerability, but a hard release-readiness blocker for any real deployment). If a deployer wires a real provider, note the callback maps unknown subjects to a 401 with no provisioning path (`router.py:256-263`).

**Recommended fix:** Implement a real OIDC token/JWKS exchange (nonce + PKCE verification, ID-token signature/claims validation) behind the adapter, or explicitly document production auth as unsupported in `docs/release/known-issues.md` and gate the startup requirement accordingly. Fix the dead branch in `create_oidc_provider`.

**Suggested regression test:** Contract test with a fake JWKS endpoint asserting a valid code produces a session and an invalid signature/nonce is rejected.

## AEGIS-OITB-003 — Release manifest verifies stale: no revision / migration-head / image-reality check

- **Severity:** Medium

- **Affected files:** `scripts/generate_release_manifest.py:200-249` (`validate_manifest`), `:17` (`DEFAULT_MIGRATION_HEAD` hardcoded); `scripts/verify_release_manifest.py:16-32`; `release/manifest.json`

**Expected:** verifying a manifest fails if it no longer describes the current tree (wrong git revision, outdated migration head, images not actually present at the recorded digest).

**Actual:** `validate_manifest` only (a) type-checks `source.revision` as a string — never comparing to `git rev-parse HEAD`; (b) never validates `migration.head` against the real `alembic heads`; (c) regex-checks image digests for `sha256:...` shape but never confirms a local image has that digest; (d) re-hashes a **fixed** artifact list, so a newly added critical artifact is simply absent with no "missing coverage" error. A manifest generated at an old commit passes at a newer commit.

**Technical cause:** verification checks internal self-consistency (checksums of a fixed list) but not correspondence to the actual release state.

**Impact:** Release attestation can pass while being stale — undermining provenance/supply-chain guarantees the manifest is meant to provide.

**Recommended fix:** In `validate_manifest`, compare `source.revision` to current HEAD (allow an explicit override for detached builds), compare `migration.head` to `alembic heads`, verify each image digest via `docker inspect` when available, and add a coverage assertion that the required artifact set is fully present.

**Suggested regression test:** Unit test that mutates HEAD/migration-head/an artifact after generation and asserts verification fails.

## AEGIS-OITB-004 — Migration/ORM index drift (`alembic check` fails; 3 DB indexes absent from ORM)

- **Severity:** Medium
- **Confidence:** High

- **Affected files:** `packages/persistence/src/aegis_persistence/orm/tables.py` (missing index declarations); migration history under `packages/persistence/.../migrations` (or repo migrations dir)

**Expected:** ORM metadata and migrated schema agree; `alembic check` is clean.

## AEGIS-OITB-005 — OIDC state store is an unbounded in-memory dict (no TTL sweep)

- **Severity:** Medium
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Directly confirmed from code
- **Affected component:** auth (OIDC login state)
- **Affected files:** `apps/api/src/aegis_api/auth/router.py:31` (`_OIDC_STATE`), `:207-211` (insert with `created_at`), `:247` (pop only on successful callback)

**Expected:** pending OIDC states expire (TTL sweep or capacity bound); `created_at` is used.

**Actual:** entries are added on `/login` and popped only on a successful `/callback`; `created_at` is stored but never read. Abandoned logins accumulate forever. Also process-local (breaks under multi-instance/horizontal scaling — a callback can hit an instance without the state).

**Technical cause:** ephemeral auth state kept in an unbounded module-global dict.

**Impact:** Unbounded memory growth / minor DoS from repeated `/login` calls; correctness failure under multiple API replicas.

**Recommended fix:** Store OIDC state in Redis with a short TTL (e.g. 5 min), or add a periodic sweep + capacity cap keyed on `created_at`; this also fixes multi-instance correctness.

**Suggested regression test:** Unit test asserting states older than the TTL are evicted and that capacity is bounded.

## AEGIS-OITB-006 — Replay read-only guard is a no-op (isolation is convention-only)

- **Severity:** Low
- **Confidence:** High
- **Directly-Reproduced-or-Inferred:** Directly confirmed from code
- **Affected component:** replay
- **Affected files:** `services/replay/src/aegis_replay/service.py:50-53` (`assert_read_only` → `return None`), called at `:113`, `:224`

**Expected:** replay paths are mechanically prevented from appending live events/state.

**Impact:** Low today (call sites are read-only), but a future edit could append during replay with nothing to stop it — a latent authoritative-state risk.

**Recommended fix:** Make the guard real — e.g. run replay on a read-only session/transaction (`SET TRANSACTION READ ONLY` or a session flag the UoW checks before `append_event`), and have `assert_read_only` assert that flag.

**Suggested regression test:** Test that appending an event within a replay-scoped UoW raises.

## AEGIS-OITB-007 — Outbox relay duplicate-delivery on crash-restart

- **Severity:** Low
- **Confidence:** Low
- **Directly-Reproduced-or-Inferred:** Inferred (from recon lead #13; not driven here)
- **Affected component:** event streaming (outbox relay → Redis)
- **Affected files:** outbox relay under `packages/event-streaming` / `services/workers` (per-claim publish in separate sessions; claim TTL reclaim)

**Observation:** the relay publishes per-claim in separate sessions; a crash mid-batch leaves rows published-but-not-marked until claim TTL reclaim, and Redis `XADD` is not idempotent. WS dedup is in-memory per connection only; DB consumer receipts exist but are not used by the relay — so a reclaim can re-`XADD` already-delivered events, and a reconnecting client may see duplicates.

**Recommended fix:** Make republish idempotent (dedup on event id in the stream/consumer receipts) or mark-then-publish with an idempotent producer; verify the reclaim path against consumer receipts before re-`XADD`.

**Suggested regression test:** Simulate a relay crash after publish-before-mark and assert no duplicate stream entries after reclaim.
